# Krypt Studio and AI agents (MCP)

Krypt Studio is an MCP server. Any MCP client, such as Claude Code, Claude Desktop, Cursor or VS Code, can read and edit the open project live: write patterns, design sounds, arrange, mix, render previews, and export the finished song with its title, artist and cover art. Every agent edit goes through the same command layer as your own clicks, so it shows up immediately and can be undone.

The built-in **Krypt Agent** panel uses the same tools through the Anthropic API with your own key.

```
 Claude Code / Claude Desktop / Cursor / VS Code …
        │  stdio (newline-delimited JSON-RPC; the client launches the shim)
        ▼
 krypt-studio-mcp.exe  (Rust shim, ~580 KB release, static CRT, serde_json only)
        │  \\.\pipe\krypt-studio-mcp-<user>   first line = {"krypt":"hello","token":…}
        ▼
 Krypt Studio (Electron main) ── MCP server (@modelcontextprotocol/server v2,
        │                        2026-07-28 and 2025-era clients on one factory)
        ▼
 Tool registry (electron/mcp/tools) ── shared/commands ── DocHost (one document, per-agent undo)
```

## Connect a client

Krypt Studio shows ready-made snippets under **Settings → Agents → Connections**. For most clients it can also write the config for you, with a `.bak` backup and without touching your other servers. The shim lives next to the app: `resources\resources\bin\krypt-studio-mcp.exe` inside the install folder. In a dev checkout it is in `resources\bin\` after `npm run engine:build`. The examples below use `<shim>` for its absolute path.

### Claude Code

```
claude mcp add --scope user krypt-studio -- "<shim>" --client claude-code
```

Then start a new session and ask, for example: *"Use krypt-studio to make a dark EDM song with a big drop."* The server's prompts appear as slash commands: `/krypt-studio:beat`, `/krypt-studio:like`, `/krypt-studio:mixcheck`, `/krypt-studio:arrange`, `/krypt-studio:focus` and `/krypt-studio:mashup`.

#### One prompt, a finished song

One request builds a complete, arranged and mixed song. The agent doesn't stop to ask questions or for approval along the way: it chooses what you left open, and every edit is undoable. Your **next** prompt edits the song ("make the drop hit harder", "darker chords", "swap the lead for a pluck"). Ask for "just a loop" or "one pattern" and you get only that.

The server instructions and the `beat`, `like`, `focus` and `mashup` prompts all walk the agent through the same build:

1. `get_playbook` for the genre (from your words, the project's genre or your library style focus). It returns the genre's recipe for this project: tempo, key, swing, every part with its sound already chosen (an instrument preset, or the best factory sample for drums), original KPN starting patterns, the arrangement in bars, the transitions at each section change, the mix plan, the mistakes to avoid, the targets, and a numbered build order of exact tool calls.
2. Every part gets a designed sound: `load_preset` / `load_sample` with the picks `get_playbook` made (the same picks `load_preset` makes for a role and genre), or `find_presets` when a part needs something else. A sound you like can be kept with `save_preset`.
3. One pattern per section with `write_pattern`, varied so no 8 bars repeat unchanged, then `transform_notes` op `groove` on the drums (and on the bass and keys where the genre swings).
4. `arrange` at the playbook's bars, `add_marker` for each section, then `add_transition` at every section boundary (risers, whooshes, swells, snare rolls or filter sweeps into drops, impacts or crashes on the downbeat, downlifters or a tape stop into breaks and endings).
5. The mix: `apply_chain` for the master, and with `insert: "new"` for the drum bus and the reverb / delay sends (the parts are routed into them); `sidechain` where the playbook ducks a part under the kick; the playbook's levels.
6. `review_song`, the mandatory self-check: it renders the whole song and lists ranked issues, each with its fix as a tool call. The agent fixes the top issues and reviews again, at most twice.
7. `set_song_info`, `commit_edit`, and a short answer: what was made, the main choices, the review score, and two or three one-line edits you could ask for next.

The agent passes any file path you give straight to Krypt Studio's tools. It never opens your audio with its own file tools, because each such call makes Claude Code stop and ask you. For more real-sounding instruments, add your own sample folders in the Browser panel (`find_samples` searches them) and import your own music into the reference library (`library_import`).

#### Make a song like this one

Plain chat works best. Drag the song file into the Claude Code window (it pastes the path) or paste its full path, and say what you want; quotes are optional:

```
make something like this "C:\Users\me\Downloads\Some Song.mp3"
Use krypt-studio to make an EDM song like this one: C:\Users\me\Downloads\Some Song.mp3
```

In Krypt Studio's own AI panel, drop the song onto the message box.

The slash forms do the same thing:

```
/krypt-studio:like C:\Users\me\Downloads\Some Song.mp3 make it edm
/krypt-studio:beat make an edm song like this song C:\Users\me\Downloads\Some Song.mp3
```

What happens next:

1. The agent calls `study_reference` with the path. With **File access** on *Anywhere on this PC* (the default), the file opens straight away. On *Ask me*, Krypt Studio asks you first about a file outside your Browser folders and the call waits for your answer: the question shows up inside Claude Code, or as a Krypt Studio dialog for clients that can't show one. On *Browser folders only* it is refused. See [Security model](#security-model).
2. The song lands muted on a track called **Reference: Some Song**, and the same call reads it on-device into a brief:
   - the tempo, as the half- or double-time reading that fits the genre;
   - the key and the swing;
   - the closest of the 18 genres, with reasons;
   - the section plan in bars, with how loud each section is against the loudest;
   - the drum feel per 16th, and the chord loop as roman numerals;
   - the loudness, tonal balance and width.
3. The song is added to a **References** collection. With a stem model installed, its deep analysis starts in the background, so `check_originality` can compare melodies with it.
4. The agent calls `build_from_reference` (the genre you asked for, else the closest one). This one call writes the whole instrumental bed of a new song in the reference's style, as **one undo step**:
   - its tempo, key and swing (from then on `set_tempo` refuses a tempo more than 3% off the reference's, or its half / double-time reading, unless the agent passes `override: true` because you asked);
   - its drum programming per section, transcribed from the drum stem;
   - its chord progression with fresh voicings, and a bass that keeps its **rhythm** on the chord roots and fifths (not its bassline);
   - its sections as patterns, arranged with markers, and transitions at every boundary (the genre playbook's kinds);
   - the closest matching sounds (fingerprints of the stems against the factory library), buses, sends and master chain from the genre playbook, the bass sidechained to the kick, and starting levels from the reference stems' loudness;
   - an **empty "Lead" channel** with a matched sound, plus the reference melody's **shape** (range, rhythm, phrase length, steps vs leaps).
5. The agent writes an **original** melody on that Lead with the shape, then runs `check_originality`, `match_mix` and `review_song`. With a reference on the Playlist, the review grades the song against it (closeness, energy shape, loudness, tonal balance, width). It fixes what they find and checks again (at most two rounds). If `build_from_reference` can't run, the agent falls back to `get_playbook`, whose recipe also follows the reference.
6. The reference stays muted and lined up with bar 1, so you can A/B it.

The line: Krypt Studio follows the reference's tempo, key, drum programming, chord progression, bass rhythm, arrangement, sound palette and mix balance. It never copies its melody, hook, lyrics, exact bassline or audio (the stems are never used as samples in the new song). Say the song is your own (`mine: true`) and the exact bass and melody are kept.

#### Mashups

`auto_mashup {a, b}` (and **Home ▸ Audio Tools ▸ Auto Mashup** in the app) makes a mashup of two songs in one call and one undo step: the vocal of one on the instrumental of the other (`vocalOverBeat`, the better way round by default), any stems of either (`stemBlend`), or the two songs trading sections (`backAndForth`, which needs no stem model). Both songs are put on one tempo (least stretch; meeting half way when keeping the beat's tempo would stretch the vocal audibly) and key (the vocal stem's notes measured against the instrumental's stems and shifted to fit best), brought to the same loudness, warped to the grid, arranged on 4-bar phrases with the hook over the drops, mixed (a light vocal chain, sends, the beat ducking under the vocal) and joined with transitions. `dry_run: true` returns the plan and a fit score with reasons and suggestions without editing anything. Mashups of songs you don't own are for practice, DJ sets you have the rights for, and personal listening, not for release.

#### Auto Mix & Master

`auto_mix {mode, preset?, prompt?, target_lufs?, true_peak?, bars?, dry_run?}` (and the Mixer's **Auto Mix**, the master strip's **Auto Master**, **Home ▸ Audio Tools ▸ Master a song**) mixes and masters without a long tool chain: it renders the song (a file per insert + gain reduction per slot), finds the vocals and each insert's role, and sets real values on its own Krypt slots (marked, so a re-run adjusts them; your other effects are never touched with `keep_user_fx`, the default). `vocals`: EQ, Krypt De-Esser, compression sized by the crest factor, the level against the beat, reverb / delay sends, a dip in the busiest bed part. `mix`: every insert's gain staging, high-pass / mud / harshness EQ, drum and bass compression, drum-bus glue, the bass ducking under the kick when their lows collide, plus the vocals. `master`: tone EQ toward the preset curve, glue, warmth, mono lows, a clipper for loud cards, the true-peak limiter last. `full`: both. It re-renders up to 3 passes (±0.5 LU, true peak never over the ceiling; a crest guard caps the loudness and says so), all in ONE undo step. Presets: Streaming Clean −14, Balanced −11, Loud Trap / Drill −8, Club / EDM −8, Warm R&B −11, Lo-fi −13, Pop Polish −9, Hip-Hop Punch −9, Rock / Live −10, Podcast / Voice −16, Phonk Slam −7 (`auto` follows the project genre). `dry_run: true` measures and lists the planned changes only.

#### Turn a song into a project

`audio_to_project {path}` (and **File ▸ Open audio as project…** in the app) converts any WAV, MP3, M4A or FLAC into an editable project: stems separated (HT-Demucs, when you installed it in Model Manager), drums, bass, chords and lead as patterns per section on matched sounds, the vocal as an audio track, sections with markers, and the stems as muted audio tracks lined up with bar 1. It opens as a **new** project (an agent is refused while the open project has unsaved changes; `into: "current"` adds the parts to the open one instead). One undo step removes it all. This is a conversion, not a new song: if it isn't your song, use the result for practice and remix study, not for release.

Use songs you own or have the rights to. Krypt Studio writes original music in a similar style; it never copies the song.

**How Claude Code passes prompt arguments.** These are Claude Code's rules for MCP prompts as slash commands:

- It splits everything after the command on whitespace and gives each declared argument one word, in order.
- It ignores quotes.
- Words past the last declared argument never reach the server.

The splitting and the dropped words are confirmed in the Claude Code 2.1.296 binary: `args.trim().split(/\s+/)`, then a zip onto the argument names. The splitting is also stated in [code.claude.com/docs/en/mcp](https://code.claude.com/docs/en/mcp.md#execute-mcp-prompts).

Krypt Studio works around this in three ways:

- **Extra word slots.** On Claude Code connections (client name `claude-code`), `beat` and `like` declare extra one-word slots (`more1` …), so a whole sentence plus a path with spaces arrives. Other clients show one form field per argument, so they only get the named ones.
- **Prose parsing.** When `bpm` / `key` / `bars` don't parse, `beat` joins every word back into the idea. Both prompts rebuild a split, possibly quoted Windows path until it names an audio file that exists.
- **Cut-off requests.** The prompt text tells the agent to read the full request from your slash command when it looks cut off. Claude Code shows the agent the full command text.

Add this to `%APPDATA%\Claude\claude_desktop_config.json`. The Microsoft Store (MSIX) build reads `%LOCALAPPDATA%\Packages\Claude_…\LocalCache\Roaming\Claude\claude_desktop_config.json`, and the installer writes both. Then fully quit Claude Desktop from the tray and reopen it.


Edit your user `mcp.json`. To open it, run **MCP: Open User Configuration**.

### Any other stdio client

Run `<shim>` with no arguments. `--client <name>` only sets the label shown in Krypt Studio until the client's own `clientInfo` arrives.

### Optional: Streamable HTTP

This is **off by default**. Turn on `settings.mcp.httpEnabled` and the server listens on `http://127.0.0.1:<httpPort>/mcp`, which is 47800 by default. Requests must send `Authorization: Bearer <token from mcp.json>` and `Content-Type: application/json`. A request with a non-localhost `Host` or **any** `Origin` header is refused, and a body over 100 MB gets `413`. Prefer the shim: it opens no network port at all.

## How the shim behaves

| Situation | What happens |
|---|---|
| App running | It relays bytes both ways. The first pipe line carries the token from `mcp.json`. |
| App closed, client asks `initialize` / `server/discover` / `tools/list` / `prompts/list` / `resources/list` | It answers from `mcp-manifest.json`, the exact answers the app captured at its last start, so clients can always list the tools. |
| App closed, client calls a tool | It launches the app detached (with `--launched-by-agent=<client>`) and waits up to 20 s, sending MCP progress if the call had a `progressToken`. If the app still can't be reached, it returns a tool error: *"Krypt Studio isn't running — start it and retry."* |
| App closed, client opens `subscriptions/listen` | It **never** launches the app for this. 2026 clients open the listen at startup and re-open it seconds after the app quits, so launching here would reopen a window the user just closed. The shim sends the acknowledgement, narrowed to the capabilities in the manifest, and holds the request. The next connection hands it to the app, and the app's duplicate acknowledgement is dropped. |
| App quits mid-session | Requests in flight get a clear error. The next call reconnects, and for 2025-era clients the shim replays `initialize`. |
| Token rotated (app restarted) | It re-reads `mcp.json` and retries the handshake once. |

One message may be up to **100 MB**: an `import_audio` upload of 60 MB of audio is about 80 MB of base64. The app frames pipe messages in linear time, and a larger message is answered with a JSON-RPC error naming the limit; the connection stays open.

Flags: `--client <name>`, `--config <path to mcp.json>`, `--no-launch`, `--print-config-path`, `--version`.
Environment variables: `KRYPT_STUDIO_MCP_CONFIG` overrides the config path, `KRYPT_AUTOLAUNCH=0` is the same as `--no-launch`, and `KRYPT_MCP_CLIENT` sets the default label.

Build the shim from the repo root so the static-CRT flags in `.cargo/config.toml` apply:

```
CARGO_TARGET_DIR=engine/target-shim cargo build --manifest-path engine/Cargo.toml -p krypt-studio-mcp
```

| `mcp-manifest.json` | the app at every start | Discovery answers for both protocol eras (initialize, server/discover, tools/prompts/resources lists) |

| `stems/<key>-<model>/` | `separate_stems` | Cached stem WAVs; a repeat separation of the same file is instant |
| `imports/<sha256>.<ext>` | `import_audio` with `data` | Audio an agent uploaded as bytes, named by its content hash: written atomically, written once (the same bytes again reuse it), checked by the engine's decoder (a file that doesn't decode is removed again). Projects reference it like any sample; Krypt Studio never deletes it on its own |
| `models/<id>/` | Model Manager (user only) | Downloaded or imported ML models, every file SHA-256-verified against the catalog |

Edited or copied-in files are picked up within a second; invalid ones are skipped and logged |
| `scripts/*.js` | Tools ▸ Scripts… ▸ Save to my library, `write_script` with `where: library` | Your Krypt Scripts (JavaScript note devices), one per file (`user:my-device` → `my-device.js`), written atomically. They only ever run inside the QuickJS sandbox |
| `packs/<id>/` | Home ▸ Sounds ▸ Sound packs (user only) | Downloaded sound packs: the catalog files (each size + SHA-256-verified), our `.sfz` mappings, `LICENSE.txt` (licence, credit, archived statement, file hashes) and `pack.json` `{id, version, installedAt}`. A download in progress lives in `packs/<id>.partial/` and is renamed only when every file verified; a cancelled one keeps its finished files for the next try. Projects refer to them as `pack:<id>/<path>` |

## Tools (101)

Kinds: **read** tools never change the project. **write** edits are additive and undoable; a request that changes nothing comes back as `isError` with *"No change: …"*, never as a fake success. **destructive** edits delete material and are still undoable. **transport** controls playback only. **history** covers undo and edit groups.

Every mutating call runs inside one DocHost history group labelled `<tool>: <summary>` (or your `change_label`) under the agent's own actor. A failed call rolls back any partial edits. The `changed:` ids in a result come from the actual document patches, so the server never claims an edit that didn't happen.

| Tool | Kind | What it does |
|---|---|---|
| `get_project` | read | **Start here.** Compact project map: tempo, time signature, swing, mode, channels, patterns, playlist lanes, markers, non-default mixer inserts |
| `list_channels` | read | Channel Rack details: instrument, sample, volume, pan, pitch, insert, root key, mono/glide, cut groups, changed parameters |
| `list_patterns` | read | Patterns with length, notes per channel, clip count, which one is active |
| `list_plugins` | read | Stock instruments and effects (`krypt.*`) plus the user's installed VST3/CLAP plugins (`vst3:<CID>` / `clap:<id>`; no VST2) |
| `describe_plugin` | read | Parameters with ranges, units and option labels; with `{channel}` or `{insert, effect}` it also returns current values and ParamRefs |
| `get_mixer` | read | Inserts, routing, sends, effect chains with changed parameters, sidechains |
| `find_samples` | read | Searches the factory sample library (kind, tags, genres, root note and bars from its index), the samples of installed sound packs (`pack:<pack>/…` paths, same metadata) and the user's Browser folders (kind guessed from file and folder names). Filters: `kind` (kick … fill, whoosh, tape-stop, swell, zap, vox, foley, ambience, retro; `fx` = any transition sound, `loop`), `genre`, `bars`, name words. Factory sounds win ranking ties. **More like this:** `like` (a `factory:` / `pack:` path, an instrument preset id, or an audio file under File access) returns the closest factory + installed-pack samples by timbre fingerprint (`similarity` %, a one-line `why` such as "darker, shorter tail"), the same kind first; `kind` searches another kind. Pack samples are measured on first use (48 per call; a warning says how many are left) |
| `find_presets` | read | Instrument presets (finished sounds with their effect chain) and effect-chain presets, factory and user, ranked by role + genre (default: the project genre) + tags + words. **More like this:** `like` (a preset id or a sample path) returns the closest factory instrument presets by timbre (`similarity` %, `why`), the same role family first; `role` searches another role |
| `get_playbook` | read | **Start here for a song.** The genre's recipe for a finished track, resolved for this project: tempo, key and swing; every part with its sound chosen (the best preset for its role and genre, or for drums the best factory sample); original KPN starting patterns; the arrangement in absolute bars; transitions per section boundary; the mix plan with resolved master, bus and send chains, sidechains and levels; the groove template; the mistakes to avoid; the targets `review_song` checks; and a numbered build order of exact tool calls. Genre: `genre`, else the project's genre, else one named in `brief`, else the reference song's closest genre, else the library style focus. With a reference song on the Playlist (`study_reference`; `reference: "none"` ignores it), the recipe follows it:<br>• its tempo reading for the genre (or the genre's own tempo when no reading fits; the sections then keep their durations)<br>• its key and swing<br>• its section plan, each section taking the playbook's parts for that kind of section<br>• its loudness and section contrast as targets<br>It also shows its drum feel and chord loop, and adds `check_originality` to the build order. With a style focus (and no reference), your references override tempo, swing, key, loudness, progressions and structure. Without a playbook for the genre it returns a generic finished-song recipe and lists the genres that have one |
| `write_pattern` | write | **Main write path.** Writes a whole pattern in KPN: replace, merge or append. Unknown channel names are created with a finished sound for the role the name implies (a factory drum sample, or an instrument preset with its effects) |
| `read_pattern` | read | A pattern as canonical KPN (or JSON with exact ticks and ids) |
| `add_notes` | write | Precise notes at `bar.step` or exact ticks |
| `transform_notes` | write | transpose (semitones or scale degrees), shift, velocity set/scale/ramp, quantize (with swing), humanize, length, legato, reverse, invert, strum, chop, and `groove` {template, amount, velocity, instrument}: the timing and accents of real drummers per 16th step (templates hiphop, funk, soul, jazz, shuffle, latin, reggae, afrobeat, rock, pop, dance). The one-prompt build grooves every drum channel with the template `get_playbook` names, and the bass and keys where the genre swings |
| `shape_notes` | write | The piano roll Tools menu: arpeggiate, glue, scale snap, flip, in-key randomize, key-range limit, velocity/pan/release/mod/fine ramps and LFOs, mute/colour/slide flags. Ops that replace notes hand the new notes to the next op |
| `generate_notes` | write | The piano roll **Generate** dialog: drafts a part into one channel in key, as one undo step. `rhythm` (Euclidean or density, accents, ghosts, 32nd rolls), `chords` (progression by degree: a preset per mood or numerals like `i VI III VII`; close / open / spread voicing, voice-led inversions, rhythm), `arp`, `melody` (contour, range, density, feel, phrases with call and response, chord tones on strong beats) and `bass` (root, root-fifth, octave, walking, 808 glides with slide notes). The arp, bass and melody follow the chords already in the pattern. `key` defaults to the pattern's key, `bars` to the whole pattern; `mode` replace or merge. Seeded: the result names the seed, the same seed gives the same notes and another seed a new take |
| `write_script` | write | Create or update a **Krypt Script**: a small JavaScript note device (`// @name`, `// @kind generator` or `transform`, `// @param` knobs and one `function run(ctx)` returning notes). The app checks the header, compiles it and runs it once on a made-up 2-bar context in the QuickJS sandbox (no I/O, no imports, 200 ms CPU, 32 MB memory); every problem comes back as `Line N: …` and nothing is saved until it passes. `where` project (default, kept in the song, one undo step) or library (`userData/scripts`) |
| `run_script` | write | Run a Krypt Script (a project script, one from the user's library, or a factory one: Euclid with probability, Markov melody, Arpeggiator, Strum and humanize, Ratchet, Velocity shaper) on one channel of a pattern as one undo step (`notes.applyScript`). `params` are the script's knobs (unknown names are errors), `seed` makes it repeatable, `bars`, `mode` replace / merge (generators), `key`. `dry_run` returns the notes as KPN and changes nothing |
| `clear_pattern` | destructive | Removes notes (whole pattern or listed channels) |
| `create_pattern` | write | New pattern, empty or cloned, with an optional fixed length |
| `select_pattern` | write | Makes a pattern the active one |
| `delete_objects` | destructive | Deletes channels, patterns, effects, inserts, automations or markers. Also `samples` (pool entries by id, name, file name or path, or "unused"; a sample still in use is refused with who uses it; removed after the channels in the same call) and `scripts` (project Krypt Scripts by name or id; the notes they wrote stay) |
| `add_channel` | write | New channel; the sound comes from the name (factory drum sample or instrument preset for its role and the project genre) or the instrument is given explicitly, with optional sample, params and insert `clone_of` (+ `with_notes`) duplicates an existing channel (instrument, sample, params, mixer insert) under the new name; volume_db / pan apply to the copy. |
| `set_channel` | write | Volume dB, pan, pitch, mute/solo, root key, mono + glide, cut groups, routing |
| `set_instrument` | write | Swaps a channel's instrument |
| `load_preset` | write | Loads an instrument preset (id, name or words like "dark pluck") onto a channel, replacing its instrument, params, sample and the effects on its own insert, or as a new channel. One undo step |
| `save_preset` | transport | Saves a channel's sound, or an insert's effect chain, as a user preset (only non-default params are stored). The sound is unchanged; a saved channel is labelled with the new preset (no undo step) |
| `set_params` | write | Many parameters in human units (`"1.2kHz"`, `"-6dB"`, `"40%"`, `"Saw"`), by channel, by effect slot or by ParamRef. Knobs inside a rack: add `chain` (name or number) and `device` (for an effect in that chain), or use the inner ParamRef `…/rack/<chainId>/…`. Reports before → after |
| `load_sample` | write | Loads a sample from the factory kit, an installed sound pack (`pack:<pack>/…`; a pack that isn't installed is refused with the pack to ask the user for) or a local audio file into a channel, or into a new sampler channel (the File access setting applies to local files) `relink`: point an existing pool sample (id, name, file name or old path; e.g. a missing file) at `sample` instead; every channel playing it follows. **Prompts:**

- `beat` (genre, bpm, key, bars, mood, idea): one prompt → a finished song ([the build above](#one-prompt-a-finished-song)), with a compact style card from the genre's playbook (any genre name or alias Krypt Studio knows: "big room" is edm, "uk drill" is drill). Your bpm and key win over the playbook's. Positional words that don't parse become the idea: bpm must be 40–250, key must read as a key, and bars must be a whole number. A song file path anywhere in the words switches the prompt to the reference workflow below.
- `like` (song, request): *make a song like this one*. The steps are:
  1. `study_reference` the song. The path goes straight to the tool, never through the agent's own file tools. It lands muted as "Reference: <name>" and comes back as a brief: tempo, key, closest genres, sections, drum feel, chord loop and mix.
  2. `build_from_reference` for the requested genre, else the closest one: the whole instrumental bed in one call (fallback: `get_playbook`, which follows the reference, and its build order).
  3. An ORIGINAL melody on the empty "Lead" channel with the returned shape, never the song's melody, lyrics or hook.
  4. `check_originality`, then `match_mix`.
  5. `review_song` (it grades against the reference too), fix, check again (at most two rounds).
  6. Leave the reference muted for A/B and answer briefly.

  When the file is missing or the path arrived cut off, the agent is told to read the full path from the command, or to ask.
- Further prompts: `mixcheck` (focus, target_lufs): a levels-and-effects pass driven by `review_song` (master chain with `apply_chain`); `arrange` (structure, length_bars): the existing patterns into sections with markers, `add_transition` at every boundary and a `review_song` check; `focus` (collection, idea): the style profile of one of your reference collections (the active focus by default) plus the playbook → compose → vary → groove → transitions → `review_song` → `check_originality` build; `mashup` (a, b, tune; all optional): one song's vocal on another's instrumental, in one go: `auto_mashup` first (`dry_run` to compare the fit when unsure which way round), then refine by hand only where it helps (`tune_vocal`, `match_clip`, `add_clip` / `remove_clips`, `add_transition`) → `render_preview` for masking → `review_song` and fixes → a short answer with variations. A missing stem model is the only reason to stop (or use `backAndForth`).

**Sounds & presets:** agents ask for sounds by **role** (kick, 808, bass, lead, pluck, pad, keys …; chains: master, drumBus, reverbSend …) plus genre and words, never by a fixed preset id; `shared/sounds/select.ts` ranks them. Factory presets ship with the app (`shared/sounds/factory`); user presets are JSON files in `%APPDATA%\Krypt Studio\presets\` (one per file, checked on load; bad files are skipped and logged). Loading a preset is one command (`presets.applyToChannel` / `presets.addChannel` / `presets.applyChain`), so it is one undo step. A channel on the master or on a shared insert gets its own insert before a preset's effects are loaded; that insert keeps feeding the bus the channel used to feed. The factory sample library's index (`resources/factory/index.json`) gives `find_samples` each sample's kind, tags, genres, root note and, for tempo-synced FX, bpm and bars. Installed sample packs (`PackDef.samples` in `shared/packs`) add their samples to that index in main (`SoundsService.factoryIndex()`, after the factory's), so `find_samples`, `load_sample`, `get_playbook`'s picks and `add_transition` use them like factory samples; the renderer gets them from `window.krypt.packs.samples()` (the Browser's **Sound packs** section, the pack cards' "Adds N sounds" line).

**Style focus:** when you set a focus in the Library panel, `get_project` says so, `get_style_profile` returns it without arguments, the built-in agent gets the profile with your message, and `commit_edit` checks the melodies written in that edit group against the deep-analysed references and appends any close match as a warning. The edit is never blocked. Details: [LIBRARY.md](LIBRARY.md).

## KPN cheat sheet

KPN (Krypt Pattern Notation) writes a whole pattern in a few lines. The parser checks every bar line, and its errors name the line and the bar: `line 3 (kick), bar 2: has 15/16 steps at the bar line (1 short)`.

```
pattern "Trap A" bars=2 grid=16 key=F#m          // header: grid = steps per bar (16 = 16ths)
kick       : x... .... ..x. .... | x... .... .x.. ..x.
snare      : .... X... .... X... | .... X... .... X..o
hat/32     : (x.x.)*7 xxxx | (x.x.)*6 xxxx xxxx    // /32 = finer grid for this line
openhat    : .... .... .... ..o. | .... .... .... ....
808 {oct=1}: F#1:6 r:4 C#2:2 E2:4 | F#1:8~ C#1:4 r:2 A1:2
```

| Step grids (drums) | |
|---|---|
| `x` `X` `o` `1`–`9` | hit (velocity 100 or `{vel=}`), accent 127, ghost 50, velocity n×14 |
| `.` `-` `_` | rest, hold the previous hit, clear the step (merge mode) |
| `(…)*n` `\|` | repeat, bar check |
| `{pitch=D4}` | which key a hit plays (default C4 = MIDI 60, the sampler root) |

| Note tokens (pitched) | |
|---|---|
| `C4` `F#2` `Bb3` | notes (C4 = MIDI 60) |
| `:n` | length in grid steps, sticky until changed (default: one beat) |
| `r` `r:n` | rest |
| `[C4 Eb4 G4]:8` | chord with explicit voicing (per-note velocity: `[C4 E4v80]`) |
| `Am7:16` `Fmaj7` `G/B` `Cdom7` | chord symbols at `{oct=}` (default 4). A letter plus a digit is always a **note**: `G7` is a note, `Gdom7` is the chord |
| `^1`…`^7` `^b3` `^#4` `^5'` `^1,` | scale degrees of `key=`; `'` goes up an octave, `,` goes down |
| `v90` `!` `?` | velocity, accent (120), ghost (60) |
| `~` | slide into the next note (808 glides); `~C4` = this note slides in |
| `@3.1` | jump to bar 3, step 1 |

Write modes: **replace** (the default) rewrites only the channels you list. **merge** sets hits, clears steps with `_` and leaves `.` alone. **append** adds the KPN after the current end of the pattern. `read_pattern` prints canonical KPN that round-trips exactly for on-grid notes; KPN velocity resolution is 1/127.

The parser, the canonical printer and the symbolic analysis are in `shared/kpn/`. `test/kpn.test.ts` round-trips 500 random patterns through the printer and the parser.

## Security model

- **No network surface by default.** Agents reach the app only through a per-user named pipe (Windows) or a Unix socket that only your user can open (macOS / Linux: mode 0600, in your private temp or runtime folder, or `~/.krypt-studio`), plus a 256-bit token that is re-generated at every launch and stored in your profile folder (`mcp.json`). Node's pipe server uses the default pipe security descriptor, so the token handshake is the access boundary. A connection without the token is dropped after one error line. The optional HTTP endpoint binds to 127.0.0.1 only, validates `Host`, rejects any `Origin`, requires the bearer token (constant-time compare), accepts only `POST` with `application/json`, and never sends CORS headers.
- **The kill switch:** Settings → Agents → off (`mcp.setEnabled(false)`) disconnects every client immediately, closes their open edit groups, and refuses every tool call until you turn it back on. The setting persists.
- **Everything is undoable.** Each agent has its own undo stack (`agent:<client>`), and the AI History panel can revert a single call, a `begin_edit` group, or everything one agent did. Agent edits never undo your own later edits; a conflict is reported instead.
- **File access** (Settings ▸ Agents ▸ File access, `settings.mcp.fileAccess`). These calls take paths from your disk: `study_reference {file}`, `import_audio {path}`, `audio_to_project {path}`, `auto_mashup {a, b}` (file paths), `load_sample`, `add_channel {sample}`, `analyze_audio` / `audio_to_pattern` / `compare_to_reference` on a file, `library_import {folder | file}`, and `set_cover {path}` (a PNG / JPEG, the only tool that may read images). All of them go through one helper (`electron/mcp/consent.ts`), which runs before the tool, outside the edit queue and the history group. There are three modes:
  - **Anywhere on this PC** (`anywhere`, the default). It's your own computer: agents connected through the local pipe (the shim your MCP client launched) and the built-in agent may open any existing local audio file or folder without a prompt. Each such read is logged (`[agent] Claude Code import_audio reads C:\… (File access: anywhere)`).
  - **Ask me** (`ask`). Files inside your Browser folders and the project's own files open directly; for anything else you are asked, as described below.
  - **Browser folders only** (`browser`). Only the factory kit, your Browser folders and the project's own files; everything else is refused with the reason (and the setting's name), never asked.
  - **The HTTP endpoint never gets "Anywhere".** When it is on, it is treated as *Ask me* at most: any local process that can read the token from your profile could talk to it, while the pipe is reached through the shim your own client starts.
  - **Always allowed, in every mode:** the files the open project already uses: samples you dropped in, recordings, stems, imports (`project.samples`, compared after resolving links). So "analyze the song I just dropped in" works through its clip, its channel and its own absolute path, even on *Browser folders only*. Plus `factory:` kit paths.
  - **Refused in every mode, never asked:** network (UNC) paths such as `\\host\share\song.mp3` or `//host/share`: just opening one makes Windows sign in to that host, which can hand your Windows login (an NTLM hash) to whoever runs it, so the check happens before the disk is touched. Also device paths (`\\.\`, `\\?\`), alternate data streams, relative paths, files without an audio extension (`shared/audio/formats.ts`, checked on the name and on the target of a link; images for `set_cover` only), links that lead to a network location, paths that don't exist, and a whole drive as a folder.
  - **Asked (Ask me mode):** you answer **Allow this file** (until Krypt Studio quits; *Allow once* for a folder), **Allow this folder**, or **Deny**. *Allow this folder* adds the folder to your Browser folders: it is saved in settings, and you can see and remove it in the Browser panel. It is never offered for a drive root.
  - **Where the question appears:** in the agent's own client when it declared the MCP **elicitation** capability (a form with one choice field):
    - On protocol 2026-07-28, which Claude Code uses by default, the call returns `input_required` with an `elicitation/create` form. The client shows it and retries the call with your answer. The server accepts only an answer to a question it asked, within 30 minutes. Claude Code shows these as a dialog ([docs](https://code.claude.com/docs/en/mcp.md#respond-to-mcp-elicitation-requests); its `Elicitation` hook can auto-answer, so don't set one up for this server).
    - On 2025-era connections, the server sends `elicitation/create` while the call waits.
    - Otherwise, or when the client's elicitation fails, Krypt Studio shows a dialog. It is parented to the main window, which flashes in the taskbar and comes forward without taking focus. The text names the client and the file, for example "Claude Code wants to use "song.mp3" … From: C:\Users\…\Downloads". **Deny** is the default button.
  - **One question at a time:** identical requests made together share one question. With no answer within 120 s, the call fails with *"The user didn't answer in Krypt Studio within 120 s …"*. A denial fails it with *"The user declined access to …"*. Every answer is logged and appears in the agent activity feed as **file access**.
  - **Dev only:** `KRYPT_TEST_CONSENT=file|folder|deny|none[@ms]` answers the dialog and `KRYPT_CONSENT_TIMEOUT_MS` shortens the wait. Packaged builds ignore both.
  - Agents can't save or open project files. They can export audio only through `export_audio` (below).
- **Exports:** `export_audio` writes only into `<Music>\Krypt Studio\` (created on first use) or, when you chose it in Settings ▸ Project ▸ *Agent exports go to*, the saved project's folder (an unsaved project falls back to Music). The agent picks at most the file name (cleaned of path characters); the file is created new with an exclusive create, so an existing file is never overwritten ("Song (2).wav"), and a failed render removes its empty placeholder. Song info and cover are written into the file afterwards, atomically (temp file + rename), without touching the audio: WAV gets a LIST/INFO chunk (what Windows Explorer reads, placed after the audio) and an `id3 ` chunk with the cover; MP3 gets an ID3v2.3 tag with the cover, the exact length (TLEN) and the encoder's gapless info (an iTunSMPB COMM frame). Explorer shows MP3 covers as thumbnails; it has no thumbnails for WAV (`shared/audio/tags.ts`).
- **Uploads:** `import_audio {data, name}` is the only other way an agent writes a file. The bytes (max 60 MB decoded; the size is checked before decoding) go to `imports/<sha256>.<ext>` inside your profile folder and nowhere else: the name is the content hash plus an extension from the audio allow-list (`shared/audio/formats.ts`), so a name with folders or `..` can't steer it. The write is atomic, identical uploads are stored once, and the engine's decoder must read the file or it is removed again. Projects that use an upload save its path and hash; on open, a missing upload is relinked from this profile's `imports/` by its hash.
- **Plugins:** agents can load the stock `krypt.*` plugins and the VST3 / CLAP plugins the user has installed and scanned (`vst3:` / `clap:` ids from `list_plugins`); third-party plugins always run in the sandboxed plugin host. Agents can't install or scan plugins. There is no code-eval tool.
- **Reference library:** agents read it and can queue a light-pass import of a folder or one song (`library_import`; outside your Browser folders you are asked first, as above). They can turn on deep analysis (`library_deep`) only when you have already installed a stem model, and they get the time estimate first; you can pause it or turn it off in the Library panel. They can't download models, delete records or files, or see a reference's transcribed notes (summaries only). Everything stays on your PC.
- **ML models:** agents use installed models only. Downloads and "Install from folder" happen only from the Model Manager UI, over HTTPS, with every file SHA-256-verified before it is used. `analyze_audio` / `audio_to_pattern` read files under the same rules as `load_sample`.
- **Sound packs:** agents read their status with `list_packs` and use installed packs only. Downloads happen only when you click Download in Home ▸ Sounds, over HTTPS, with every file size- and SHA-256-verified before the pack is installed. A source that only publishes a ZIP is verified as a whole, then only the catalog's listed members are extracted (each checked by its own size and SHA-256, written atomically, never outside the pack folder) and the archive is deleted.
- **Krypt Voice:** `generate_voice` / `sing_notes` render locally (Kokoro in the analyzer, offline) or, with a Cloud voice, send the text or lyrics to Fish Audio with the key the user saved (encrypted with DPAPI; never logged, returned or given to clients; every Fish request is logged as "sent to Fish Audio"). Cloud voices are Fish's own licensed voices or the user's own clone, never a community voice. Agents can't set the key, clone a voice or remove one: cloning happens only in Settings ▸ Voice, from a take the app's recorder made in this session that starts with the consent line, with the user's confirmation.
- **Long calls:** `separate_stems`, `audio_to_pattern`, a first `analyze_audio`, `generate_voice` / `sing_notes` (the analyzer's `tts` / `sing`), and `match_clip` / `tune_vocal` on audio that hasn't been analysed yet can take seconds to minutes. When the client sends a `progressToken`, the server streams `notifications/progress` with the analyzer stage; cancelling the request cancels the analyzer job.
- **Prompt injection:** names returned in results are stripped of control and bidirectional characters and capped at 80 characters. The server instructions and the agent prompt say that names are user data. Tool descriptions are static and never built from project data.
- **Destructive tools** carry `destructiveHint`. When `settings.mcp.requireConsentForDestructive` is on, they also carry `_meta["anthropic/requiresUserInteraction"]`, so Claude clients ask before each call. In-app confirmation dialogs are not implemented yet; undo is the safety net.
- **The API key** for the built-in agent stays in the main process, encrypted with DPAPI. It is never sent to the renderer, written to logs, or given to MCP clients. Without secure storage, the app refuses to save the key.
- **No telemetry.** The activity feed (`mcp:activity`) and the logs are local only.

## Krypt Agent (built-in panel)

- Uses `@anthropic-ai/sdk` in the main process, model `settings.agent.model` (default `claude-opus-5-5`), with adaptive thinking at effort `medium`. It runs a manual streaming tool-use loop over the same tool registry, as actor `agent:krypt-panel`.
- **Prompt caching:** the tool list is in deterministic order and the system prompt is frozen (role, workflow and the full KPN reference). Both carry `cache_control` breakpoints, and automatic caching covers the growing conversation. Project state is attached to your message, never to the system prompt.
- **Safety:** refusals are re-run server-side with `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`) on models that support it. A refused turn is reported, never executed. A tool call cut off by `max_tokens` is not run. History is append-only.
- **Style focus:** when a focus is set, its profile (and your brief) is attached to your message in a `<style_focus>` block whenever it changes, never to the cached system prompt.
- **Events:** the agent streams text deltas, `tool_use`, `tool_result`, and finally `done` with token usage and an estimated cost in USD. **Stop** aborts the request and closes any pending tool call. A single message is limited to 30 model steps.
